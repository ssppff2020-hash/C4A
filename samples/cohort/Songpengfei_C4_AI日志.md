# Songpengfei C4 AI 日志：lesson-design-assistant 的制作过程

> 挑战：C4 技能分享与传播 ｜ 作者：Songpengfei ｜ 版本：**v2** ｜ 日期：2026-10-07
> 本文记录 v1（初版成型）与 v2（对照官方样例做差距分析后的修复与增强）两轮完整过程。

---

## 一、用到的 AI 工具

| 阶段 | 工具 | 用途 |
|------|------|------|
| v1 | 腾讯混元 Hy3 + DeepSeek-V4 Pro（Marvis 本地文件智能助手） | 理解挑战要求、设计技能架构、撰写文档初稿 |
| v1 | Python 脚本执行环境 | 运行 `lesson_design_template.py`、打包 .skill、绘制 demo 截图 |
| v1 | 图片理解模型（analyze_image） | 验证 demo 截图渲染是否正常 |
| **v2** | **Claude Code（终端内 Agent，可读写文件/执行命令/看图）** | **差距分析、写 `lesson_check.py`、修编码 bug、重打包、重绘 demo、补 README 与传播包** |
| v2 | Python 3.11 + Pillow 12（仅用于生成 demo 图，**不进技能包**） | 重绘 demo（标题自动缩放、矢量绘制对勾） |

## 二、怎么指挥 AI 的（关键 prompt 与思路）

1. **需求理解 prompt**："通读挑战说明，提取 C4 交付物清单、命名规范、评判标准。"
   → 得到 5 类交付物（skill 说明 / 可执行内容 / demo / 教学说明 / AI 日志）、命名规范（姓名_C4_xxx）、评分维度（技能质量 25 / 可教性 20 / 产物完整性 15 / AI 使用 20 / 复盘 20）。
2. **技能方向确认**：通过交互确认用户真实高频可复制能力 → 选定"AI 辅助教学设计（教案/大纲/学情分析生成）"，与高校教师身份高度契合。
3. **架构设计 prompt**："参考材料中两个示例技能（wechat-doc-mapper 脚本驱动型 / skill-explainer 指令驱动型），设计一个输入输出明确的 8 段式教学设计技能。"
   → 确定技能形态为"指令 + 脚本 + 数据"混合型，定义 Clear I/O 与 6 步工作流。
4. **骨架生成 prompt**："写一个纯标准库 Python 脚本，--topic/--audience/--duration 参数化生成 8 段式 Markdown 骨架。"
   → 产出 `lesson_design_template.py`，作为技能的可执行脚本（确定性任务部分）。
5. **数据文件 prompt**："把学情分析维度、布鲁姆目标动词库、环节模板、评估规则整理成 YAML，供按需加载。"
   → 产出 `references/design_framework.yaml`。
6. **文档撰写 prompt**："按挑战命名规范生成 skill 说明 / 教学说明 / AI 日志，内容要覆盖评分信号的每一项。"
   → 产出 3 份交付文档。

### v2 阶段的关键 prompt

7. **差距分析 prompt（本轮最有效的一句）**：
   > "把 materials/ 下那两个官方 `.skill` 样例解包，和我做的 `Songpengfei_C4_lesson-design-assistant.skill` 逐层对比——
   > 结构、打包格式、SKILL.md 写法、脚本能力，列出所有差异，并指出哪些差异会让别人**装不上**或**看不懂**。"
   → 直接揪出 tar.gz/ZIP 格式不符、缺校验能力等 4 个缺陷。

8. **校验器设计 prompt**：
   > "写一个纯标准库的 `lesson_check.py`，对 8 段式教案做机械校验：结构完整、目标动词可测量、环节时长合计=课时、
   > 目标-评估对齐、评估双类型、学情假设标注、自查清单。输出 0–100 分与逐条建议，支持 `--json`。
   > **关键要求：不许对未填充的空骨架给高分**——用你自己的脚本造一个空骨架验证一下。"

9. **反向验证 prompt（防止自欺）**：
   > "故意造一份残缺教案（删掉评估与反思段、把环节时长改成合计 35 分钟、目标改回『掌握/熟悉』），
   > 跑校验器，确认它判低分并逐条指出问题。如果它还是给高分，说明评分逻辑有问题，回去改。"

10. **陌生人回环测试 prompt**：
    > "把发布用的 `.skill` 解包到一个全新目录，严格按 SKILL.md 里 Quick Start 的三条命令执行，
    > 看看不依赖你的开发环境能不能跑通。有任何一步失败就报告。"

## 三、迭代过程（6 轮）

### 第一阶段：v1 从零成型

| 轮次 | 做了什么 | 发现的问题 / 改进 |
|------|----------|-------------------|
| R1 | 阅读挑战材料，理解要求与评分标准 | 无——材料齐全 |
| R2 | 设计技能架构、写 SKILL.md v1 | 初版环节只有笼统描述，缺少"目标-活动对齐检查"与边界情况表 → 补充对齐规则、Edge Cases、自查清单 |
| R3 | 写脚本并测试运行 | 首次用 python_executor 传参失败（执行环境不支持命令行参数）→ 改用 shell 执行验证脚本；Pillow 缺失 → 安装后重试 demo 生成 |
| R4 | 打包 .skill 并验证包结构 | 用 tarfile 解包确认 SKILL.md / scripts / references 三要素齐全；analyze_image 验证 demo 截图渲染正常 |

### 第二阶段：v2 对照官方样例做差距分析

v1 交付后我没有直接收工，而是提出一个检验问题："**材料里那两个官方 `.skill` 样例，和我的包到底差在哪？**"
于是把 `materials/` 下的 `wechat-doc-mapper.skill` 与 `skill-explainer.skill` 都解包逐层比对，一次暴露出 4 个真实缺陷。

| 轮次 | 做了什么 | 发现的问题 / 改进 |
|------|----------|-------------------|
| R5 | 解包官方两个样例，与自己的包逐项比对 | 发现 **4 个真实缺陷**（见下），其中 2 个会导致"别人装不上/看不懂" |
| R6 | 逐项修复 + 新增校验器 + 重绘 demo + 补传播包 | 打包格式改为 ZIP；新增 `lesson_check.py`；两个脚本加 UTF-8 兜底；demo 图重绘；补 README 与传播包 |

**R5 查出的 4 个缺陷（这是本轮最有价值的产出）：**

| # | 缺陷 | 怎么发现的 | 为什么严重 |
|---|------|-----------|-----------|
| 1 | 我把 `.skill` 打成了 **tar.gz**，而官方两个样例实测是 **ZIP**（文件头 `PK\x03\x04` vs `1f8b 0808`） | 读文件头 + 解包对比 | 格式不对 → 别人**可能根本装不上**，直接违反"可复用" |
| 2 | 技能只有"生成"没有"验证"，「可验证」是嘴上说的 | 对照四条件逐条自问"证据在哪" | 挑战明确要求"给定输入 X 得到预期输出 Y"，没有校验器就没有硬证据 |
| 3 | 骨架脚本在 Windows 控制台输出中文**全是乱码** | 实际跑一遍看 stdout | Windows 默认 GBK，`print` 中文直接乱码——文档写了命令、用户却拿到乱码，属"别人按说明操作会失败" |
| 4 | Demo 图标题**超宽被截断**（右端 "— Dem" 被裁掉），✅ 渲染成豆腐块 | 看图 | 这是"可教性/演示"的第一印象，截图截断显得很业余 |

**修复过程中的二次发现（修复本身又踩了坑）：**
- 校验器初版写完，我拿**未填充的空骨架**测了一下——结果它给了 **83 分"通过 ✅"**。
  这暴露出评分设计过度奖励"标题存在"：只要 8 个标题在，空表也能及格。→ 增加**占位符检测 + 分数上限门控**：
  未填充小节 ≥3 时总分上限 40 分并强制判 FAIL。空骨架分数从 83 降到 40。
- 修复后又做了**反向验证**：故意造一份残缺教案（删段、改时长、目标退回"掌握"），
  确认校验器能判 26 分并逐条给出修改建议——**一个只会打满分的校验器是没有价值的**，必须证明它会报错。
- 打包完成后做**陌生人回环测试**：把发布用的 `.skill` 解包到全新目录，严格按 SKILL.md 的 Quick Start 三步执行，
  确认不依赖我的开发环境也能跑通。

## 四、我（人类）做了什么 / AI 做了什么

| 环节 | 分工 |
|------|------|
| 需求定义 | 我：选定技能方向（教学设计），确认署名与交付规范 |
| 架构设计 | AI：参照示例技能提出"指令+脚本+数据"混合形态与 8 段式输出结构；我：决策采用 |
| 内容创作 | AI：撰写 SKILL.md / 教学说明 / AI 日志 / 示例教案全部正文；我：审查结构、补充教师视角的坑与 FAQ |
| 工程实现 | AI：写脚本、打包、绘图；我：设定输入输出参数、确认演示案例（数据结构—栈） |
| 质量把关 | 我：用挑战 rubric 五维自查（技能质量/可教性/完整性/AI 使用/复盘）；AI：按自查结果修订 |
| **v2 差距分析** | 我：提出"和官方样例差在哪"这个检验问题，定下"必须能装、必须有校验、必须会报错"三条验收线；AI：解包比对、逐项定位缺陷、写校验器与修复 |
| **v2 反向验证** | 我：坚持造反例（空骨架、残缺教案）验证校验器会报错；AI：实现占位符检测与分数门控，并跑通三种输入的对照 |

## 五、AAR 复盘（反思）

### 做得好的
1. **先理解后动手**：通读挑战说明与 rubric 后才设计，避免交付物跑偏。
2. **技能形态选型正确**：混合型技能兼顾确定性（脚本出骨架）与灵活性（AI 填充内容），比纯指令型更"可执行"。
3. **IO 先行**：先用一句话写死"输入____输出____"，后续所有设计（8 段结构、6 步工作流）都围绕它展开，没有迷失。
4. **v2：拿官方样例当"标准答案"做差距分析**——这是本轮最有效的一招。与其凭感觉判断自己做得好不好，不如把现成的合格样本解包，逐层问"我这层和它差在哪"。4 个缺陷里有 3 个是这么揪出来的。
5. **v2：坚持反向验证**。校验器写完先拿空骨架和残缺教案试，确认它会报错。**一个只会打满分的检查器没有价值**——如果不做这步，我会交付一个人人 100 分的废脚本还以为很成功。

### 踩过的坑（失败经验）
1. **python_executor 传参失败**：脚本测试时误以为脚本有 bug，实际是执行环境不支持命令行参数。教训：脚本类技能要写明"可用 shell 直接运行"，并在文档中给出一行命令示例。
2. **Pillow 缺失**：demo 绘图第一轮失败。教训：环境依赖要先确认，技能脚本应坚持"纯标准库"原则——因此 `lesson_design_template.py` 设计为零第三方依赖，保证可复用性。
3. **打包格式想当然**（v2 发现）：挑战文档写"`.skill` 就是 tar.gz"，我照做了。但解包官方两个样例发现它们是 **ZIP**。教训：**文档措辞 ≠ 实际交付物**，判断标准要落在"官方样例文件头"这种可验证的证据上，不能只信文字说明。已改为 ZIP 主交付 + tar.gz 备选。
4. **Windows 中文编码**（v2 发现）：脚本在 Windows 控制台 print 中文全部乱码（默认 GBK）。我是在自己机器上跑了一遍才发现的——**如果只看代码不实际运行，这个坑会直接留给每一个 Windows 用户**。教训：跨平台脚本必须显式设置 stdout 编码，并把"实际运行"作为交付前的固定动作。
5. **校验器初版评分设计失衡**（v2 发现）：空骨架拿到 83 分"通过"。原因是评分只看"标题是否存在"，不看"内容是否填了"。教训：**评分函数自己也需要被测试**——用最差的输入去测，看它会不会误判为通过。
6. **截图不检查细节**（v2 发现）：v1 的 demo 图标题超宽被裁掉、"✅"渲染成豆腐块，我交出去时没看。教训：demo 是"可教性"的第一印象，**交付前必须真的看一眼图片**，不能假设代码没报错就等于图没问题。

### 改进方案（v3 计划）
1. 增加"教学大纲（整学期）"模式：输入课程名与周数，输出分周教学计划。
2. 增加"教案转学校模板"适配层：常见高校教案模板一键映射。
3. 把学情分析升级为"可挂接前测数据"：用户粘贴问卷结果，AI 自动生成差异化策略。
4. 校验器增加**内容质量启发式**（不只是结构）：如检测"设计意图"是否只是复述环节名、评估观测点是否具体可比对。
5. 基于 `传播包.md` 收集到的真实反馈，把最高频的 3 条吐槽直接做进 v3，并公开记录"这条是被谁提的"。
6. ~~增加学科案例库~~ ✅ v2 已完成（6 个学科）

## 六、传播计划（对应挑战"被使用次数"核心指标）

C4 公认的最高权重是**被使用次数**——技能再好，没人用也是低分。
所以 v2 专门补了一份 `Songpengfei_C4_传播包.md`，把"传播"从一句口号拆成可以照抄的动作：

| 时间 | 动作 | 产出 |
|------|------|------|
| D1 | 群内发布（传播包已备好三版文案，按场景挑一版直接发） | 首批下载 |
| D2–D3 | 私聊 3 位正在备课的同事，**由我帮他们跑**（降低对方行动成本） | 3 份真实教案 |
| D4 | 把真实输入→真实输出（脱敏）发群二次曝光 | 观望者转化 |
| D5–D6 | 用统一反馈表收意见，整理 Top 3 吐槽点 | 反馈清单 |
| D7 | 按反馈出 v3，公开发布"改了哪几条、是谁提的" | 迭代闭环 |

传播包内含：**发布文案 ×3（一句话版/标准版/故事版）、点对点邀请话术（区分同事/督导/比赛）、
30 秒反馈表、传播追踪表、7 天计划、6 条常见提问应答**。

> 追踪表就是"被使用次数"的证据链，也是 v3 改什么的决策依据。
> 挑战文档说传播链是「发布 → 别人提问 → 你帮助 → 别人成功使用 → 反馈改进 → 迭代 v2」——
> D7 的 v3 发布就是这个闭环的收口。
